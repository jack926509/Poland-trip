## 1. 為什麼要做這件事

現有網站是「桌機分章雜誌 ＋ 手機四分頁 PWA」的雙軌設計，資料放在 `redesign/data.js`。後來另外收集了一份更新、更完整的四城市指南 `poland-travel-guide-final.html`（含米其林 2026、門票速查、市內交通、伴手禮、超商），兩份資料各自獨立、互不相通，而且**內容有 12 處互相矛盾**（詳見第 6 節）。

這次要做的是：拋棄舊的視覺設計與頁面架構，把兩份資料合併成單一來源，用一套新的視覺重新產生整個網站。

## 2. 做完之後你會得到什麼

一個約 20 頁的靜態網站，電腦瀏覽器打開後：

- 首頁看得到整趟行程的總覽，點得進任何一天、任何一個城市
- 每天一頁：當天的時間表、車班、景點、當天該注意的事
- 每個城市一頁：真實比例的互動地圖（可縮放、點圖釘看說明）、景點表、餐廳表
- 實用資訊分頁：訂票時程、米其林餐廳、門票速查、市內交通、伴手禮、行前提醒等

之後要改內容（例如票價變了、換一家餐廳），只要改一份資料檔，重跑一次產生指令，20 頁會一起更新——不用逐頁手改。

**方向：編輯誌感排版（A）＋ 真實比例地圖（C）**

## 6. 資料衝突處理原則（重要）

> **本節只講原則。逐筆的裁決結果一律以 `docs/資料校正表.md` 為準**——那份表是四個獨立角度審查後彙整的，共 28 筆，實作時照那張表選邊，不要臨場自行判斷。

四個角度的審查（跨檔比對、data.js 內部、HTML 內部、行程時序可行性）共查出 **28 筆**問題：6 筆會導致撲空或走錯（🔴）、10 筆資料打架已裁定（🟡）、9 筆顯示層瑕疵（🔵）、3 項需上官網查證（❓，另有 1 項與 🔴 的皇家城堡重疊、不重複計數）。

### 預設規則：以 `poland-travel-guide-final.html` 為準

理由：它是較近期（2026-08）收集的版本，且檔案本身多處標註「已更新（原標 XX）」，代表收集時已做過查證。

**但這個預設規則有兩筆反向例外，且 HTML 自己內部也有 6 處矛盾**——它「較可信」是相對的，不是絕對的。詳見校正表。

### 三筆高風險衝突（會實際影響行程，需特別處理）

| # | 項目 | 舊資料說 | 新資料說 | 處理 |
|---|---|---|---|---|
| 1 | 華沙 Neon 霓虹博物館**地點** | 在 Praga 區 | 已遷入科學文化宮 4 樓 | 採新資料。照舊資料帶路會撲空 |
| 2 | 波茲南古市政廳博物館 | PLN 10 可入場 | 2026/7/1–2027/11/30 整修閉館 | 採新資料，並在頁面明確標示「整修中，僅能外觀」 |
| 3 | 華沙皇家城堡票價 | PLN 50/40/100 | 30–110 多階（博物館 60/45、城堡路線 95/75、宮殿 30/20、金票 110/90） | 採新資料的多階體系 |

### 兩筆反向例外：舊資料才是對的

1. **樂斯拉夫百年廳 10/28 圓頂展廳**：舊資料明確寫「10/28（正好是本行程當天）圓頂展廳不開放」，且註明查證自官方預約日曆；新資料只泛稱「偶因活動關閉」。**採舊資料的明確警示**，並保留新資料「行前 3–5 天上 halastulecia.pl 再確認」的建議。

2. **日落時間**：新資料寫「DST 後日落約 15:35–15:50」，**這是錯的**。用天文公式驗算過，行程期間實際日落為華沙 10/26 的 16:14 到華沙 10/31 的 16:04（樂斯拉夫 10/28 為 16:29），舊資料的 16:34 才接近正確。網站一律採「行程期間日落約 16:05–16:30」。錯用 15:35 會平白砍掉每天約 40 分鐘的戶外規劃時間。

### 其餘裁決

其餘票價與敘述類衝突一律採新資料，逐筆結果見校正表第 2 節。其中「Auschwitz 訂票開放時間」兩邊差距最大（90 天 vs 2–3 週），採新資料但加註「建議行前自行至官網確認」。

### 四項無法從資料判斷、需上官網查證

皇家城堡冬季開放時間（最高優先，Day 7 行程成立與否全看它）、辛德勒工廠週日最後入場、Auschwitz 訂票開放時間、MOCAK 與 Galicia Jewish Museum 週一是否公休。網站上這四項要標成「待確認」，不可寫得像已確定。

### 標註原則

所有票價、開放時間類資料，頁面上統一加註資料查證日期（2026-08），並標明「實際以官網為準」。

## 7. 技術架構

### 產生方式

一份資料 ＋ 一組模板 ＋ 一支產生腳本 → 產出靜態 HTML。

```
src/
├── data/          # 內容資料（見第 5 節）
├── templates/     # 頁面模板：layout（共用外殼）、day、city、practical、home
├── styles/        # CSS
└── build.mjs      # 產生腳本
dist/              # 產出的靜態網站（部署目標）
```

- **執行環境**：Node.js，用內建模組即可，不引入前端框架（不用 React、不用 esbuild）
- **模板作法**：JavaScript template literal（樣板字串），不引入樣板引擎
- **產出**：純靜態 HTML + CSS + 少量 JS（只有地圖需要 JS），不需要伺服器
- **外部依賴**：僅 Leaflet（地圖）與 Google Fonts，兩者都用 CDN，與現有作法一致

### 產生指令

```bash
npm run build     # 產生全部頁面到 dist/
npm test          # 驗收：檢查頁數、必要元素、資料完整性
```

專案目前沒有 `package.json`，本次要建立。

### 部署

沿用現有管道：推送 `main` 後由 GitHub Actions 部署，三個對外網址都會更新：

- `polandtrip.xiehnet.com`（正式站）
- `jack926509.github.io/Poland-trip`（GitHub Pages）
- `poland-trip-7wm.pages.dev`（Cloudflare Pages）

⚠️ 已知陷阱：**`poland-trip.pages.dev`（沒有 `-7wm`）是另一個無關的 app**，驗證部署結果時不要抓錯網址。

`prepare-site.sh` 的 allowlist 是為舊結構逐檔寫死的（`prepare-site.sh:16-28` 明確列出 `redesign/`、`desktop/`、`B-companion.js` 等舊檔），改版時必須整段改寫成對應新的 `dist/` 結構，否則部署出去的會是舊檔案或空站。

## 10. 這次不做的事（避免範圍膨脹）
