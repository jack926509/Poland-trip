- 已公開：旅遊日期、航班號碼與時間、住宿名稱、公開地址、地圖座標、景點與交通規劃。
- 不公開：旅客姓名、護照或證件號碼、訂位代碼、票號、付款資料、房號與私人聯絡方式。
- 火車時刻標示為「參考班次／尚未訂票」時，只代表已選入規劃；完成指定日核實及購票後才可視為成立。


## 離線能力

出國漫遊時網路不穩，所以站台刻意不依賴外部 CDN 執行：

- `sw.js` 是真正的快取 service worker，安裝時預快取 23 頁與 CSS／JS／城市主圖。
  頁面走 network-first（有網路拿最新），靜態資源走 cache-first，
  OpenStreetMap 圖磚走 stale-while-revalidate 並限制在 400 塊以內。
- Leaflet 自行 host 於 `vendor/leaflet/`，建置時複製到 `dist/assets/leaflet/`，
  單檔版則直接內嵌。**升級 Leaflet 時請一併更新 `vendor/leaflet/`**，
  並確認檔案是 LF 換行（上游 `leaflet.css` 是 CRLF，會讓 `git diff --check` 失敗）。
- 字型仍走 Google Fonts，但改為非阻斷載入：CDN 連不上時內文立即以系統中文字型顯示。
- 地圖載入失敗時 `.map-container` 會顯示說明文字，引導改用景點清單的 Google Maps 連結。

離線實測方式：`node build.mjs` 後以任一靜態伺服器服務 `dist/`，
載入首頁待 service worker 啟用，再切離線走訪各頁。

## 儀表板與訂票狀態維護

- 儀表板在開啟、每分鐘、切回頁面及匯出前，依台灣日期重新計算今日更新量和逾期數；離線時也可計算，但使用的是已載入的資料，沒有自動查票。
- JSON 與 CSV 使用匯出當下的日期及相同統計；CSV 採 UTF-8 BOM、CRLF 換行，所有欄位皆處理引號。
- `src/data/trip.js` 的 `todoGroups` 為人工訂票紀錄。查核後更新 `status`、`checkedAt`（實際查核日期）、`recheckAt`（下次查核期限）、`action` 與 `url`。缺少查核日期時顯示「未記錄，請重查」，不以建置或部署日期代填。
- 「可查／購」仍計入未完成項目。只有收到訂票確認後才改為「已訂妥」或「已完成」，並核對 `days`、`trains`、`reservations` 與 `bookingTiers` 的相應行程；票號、訂位代碼與付款資料另存私人票券。
- 資料庫 CSV 匯入只更新 `travel-database.js` 的對應條目，不會替使用者完成購票或自動更新 `todoGroups`。修改後執行 `env -u NODE_OPTIONS ./verify.sh`，再提交部署。

## 2026-09-14 時間資料結構化：訂票倒數、行程稽核、日照與今日卡

這輪處理的是同一個根因：**站上所有時間都是寫給人看的自由字串，程式讀不到**。
`steps[].t` 有 `'16:15'`、`'參考 10:58'`、`'18:35 前'`、`'13:30–15:00 預留'` 四種寫法；
日落只寫在行前提醒的一段散文裡；火車開賣日是 `trains[].saleOpens` 欄位，
但沒有任何地方會提醒還剩幾天。於是「這步驟晚於末入場了嗎」「轉場還剩幾分鐘」
「戶外行程排到天黑之後了嗎」全部只能靠人腦記。

**共同地基 `src/lib/schedule.mjs`**——只讀不寫，`steps[].t` 的原文是既有輸出與
測試的契約，維持不變；需要額外語意時另立並行欄位。`parseStepTime` 把時刻分成
exact／reference／estimate／deadline／window 五種語意，讓稽核能區分「計劃時刻晚了」
與「硬截止破了」。測試涵蓋現有全部 72 個步驟時刻皆可解析。

**訂票倒數看板**（`practical/booking.html#countdown`，首頁顯示最近一項）——
四段城際火車 9/25–9/28 陸續開賣，PKP 是階梯票價且每段都銜接當晚轉場。
火車開賣日不重抄進 `deadlines`，由 `collectDeadlines()` 於建置時併入，
兩邊不會各自漂移；手動維護的十筆每筆都帶 `basis` 欄位寫明日期怎麼來的。
整表在建置時渲染完成，前端只依 `data-countdown-*` 更新剩餘天數，
因此離線開啟或分頁過夜倒數都還是對的。

**行程稽核 `npm run audit:schedule`**——七條規則，依誤判成本分級：

| 規則 | 嚴重度 | 檢查 |
|---|---|---|
| 步驟順序 | 擋 build | 同日時刻不得倒退 |
| 星期標示 | 擋 build | `date` 的中文星期須與推算相符 |
| 場館引用 | 擋 build | `constraint.venue` 須指得到 `venueHours` |
| 末入場 | 提醒 | 步驟不得晚於該館最後入場 |
| 轉場緩衝 | 提醒 | 發車前最後一步的餘裕（門檻 30 分） |
| 公休日 | 提醒 | 當日逢公休仍排了行程 |
| 拍照光線 | 提醒 | `lightPhase` 宣告須與當日日落相符 |

新增 `tickets.js` 的 `venueHours`，只把既有 `note` 已查證的內容轉成欄位，
不新增未經查證的開放時間；`lastEntry` 為 null 時稽核跳過而不猜。
目前零結構錯誤、一則警告（Day 3 巴士 06:45 報到距 07:10 發車 25 分鐘，屬刻意安排），
測試釘住這個數字。

**日照結構化**——10/25 凌晨夏令時間結束，日落從 Day 1 的 17:23 掉到 Day 2 的 16:30，
整趟旅程的戶外可用時間在第二天就少掉 53 分鐘。`essentials.js` 新增 `daylight` 八筆，
散文那條改為指向本表；每日行程頁多一張日照卡，行前提醒頁多一張八日總表，兩者同源。
`photoSpots` 新增 `lightPhase`，不改寫 `bestTime` 的顯示字串——要驗證的是意圖與
天文值是否一致，不是重寫給人看的文案。

**今日卡 `today.html`（第 24 頁）**——旅途中單頁速查：今天不能延誤什麼、住哪
（波蘭文地址可直接出示）、幾點的車、今晚吃哪、日照、備案、緊急電話。
八天全部靜態渲染，前端只決定顯示哪一張；卡片不預先 `hidden`，
沒有 JavaScript 時八張全部可讀。日期以華沙當地時間判斷（行前倒數看台北）。
選日腳本走內嵌模式而非外部 script——單檔版只打包 `<main>`，外部 script 會被丟掉；
選取器一律用 `data-*`，因為單檔版會替每頁的 id 加前綴。

> 新增頁面要同步七處：`sw.js` 預快取、`standalonePages`、導覽分組切片、
> `htmlCount`、`build.test.mjs` 的頁數斷言、搜尋索引與 `sitemap.xml`。
> 這次漏掉 `sw.js`（離線正好打不開這一頁），由既有測試抓到。

**倒數看板合併第三個來源**——自由行資料庫的 `recheckAt` 原本只在資料品質面板
以「逾期」形式出現，等於第三份互相競爭的期限清單。合併後倒數是唯一入口，
各來源的正本仍留在原處（`trains[].saleOpens`、`databaseEntries[].recheckAt`），
`collectDeadlines()` 只讀不抄。

資料庫項目與手動項目不是重複，是不同粒度：資料庫的「景點票券與入場時段」
是所有票券的進度彙總，手動的「10/03 前訂 Wieliczka 英語場」是具體動作，
而且資料庫的日期通常更早——它們是「確認要訂什麼」的前置步驟。

> 合併時發現一筆真衝突：資料庫的 ETIAS 重查日是 **2026-09-24**，
> 但手動推算的期限排到 **10/10**，晚了 16 天——倒數若照手動那筆走，
> 等於悄悄把既有期限放寬。已刪除該筆，ETIAS 只保留出發前最後確認（10/21），
> 並在 `basis` 註明與資料庫項目的互補關係。新增守門測試三項：
> 每筆待處理的資料庫重查項目都必須出現在倒數、合併後 id 不重複、
> ETIAS 手動期限不得早於或取代資料庫的重查日。

合併後倒數共 26 筆，最近一筆由 T-11（火車開賣）前移為 **T-9（車票重查，9/23）**
——開賣前兩天要先重新核對班次，這才是真正的下一件事。

**日照數值改為可重算**——自我檢核時發現人工填入的 Day 1–4 日落早了 26–31 分鐘、
八天日出有七天有誤，而且錯的剛好是沒有從已查證來源抄過來的那幾天：
Day 5–8 的日落是從專案 2026-08-11 查證的散文抄來的，四筆全對；Day 1–4 是憑印象填的，四筆全錯。

新增 `tools/sun-times.mjs`（`npm run sun:times`）以天文演算法推算，
校驗基準是那四個人工查證值，演算法四筆吻合到分鐘。`daylight` 表改由演算法產生，
`tests/daylight.test.mjs` 逐筆比對，數字不會再默默漂掉。
`blueHourEnd` 同時改為民用曙暮光結束（太陽 −6°），不再是固定加 30 分鐘。

> 影響：Day 1 華沙實際日落 **17:23**（不是 16:52），是全程光線最長的一天；
> 克拉科夫三天各比原記載多約 26 分鐘的戶外時間。原本「少掉近一小時」的敘述
> 方向正確但數字失準，實際為 53 分鐘。

**自我檢核抓到的其餘問題**：

| 問題 | 性質 |
|---|---|
| 倒數看板呼叫 `getTaipeiToday`，內嵌後頁面上只有 `taipeiToday` | **執行期錯誤**，前端重算完全沒跑 |
| `venueHours` 的 POLIN 公休日是憑印象補的，站內無來源 | 違反該檔自訂的「不新增站內沒有的事實」 |
